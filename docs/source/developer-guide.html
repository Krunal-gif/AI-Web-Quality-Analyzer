1 · The idea

What the tool does

You give it a website, a project folder or one file. It finds problems, explains them, suggests fixes — and changes nothing until you approve.

Provide target→Analyse→Detect issues→Explain why→Show before→Suggest fix→Your approval→Apply→Show after→Final report

1. Find

49 rules check SEO, accessibility, HTML structure, content, code and security. Each issue knows the exact file, line and piece of code.

2. Explain & fix

Every rule has a built-in "why it matters". Many rules also create a fix. Ollama (local AI) can write a better explanation and corrected code.

3. You decide

Approve, reject or edit each fix. Write one fix straight into its file, or apply them all as a patch or into your files. A re-scan proves each fix worked.

3 · How it works

What happens when you click "Analyse"

Follow one request through the code — this is the most important path to understand.

1React App.jsx → analyze() sends POST /api/analyses with the target.
2routes/web.php sends it to AnalysisController@store.
3Analysis::create() starts a new analysis with a unique id.
4SourceLoader::load() reads the folder/file — or downloads the web pages — into Document objects.
5RuleEngine::analyze() runs HtmlRules, CodeRules, SiteRules on every document → a list of Issue objects.
6Scoring::score() turns the issues into 0–100 scores per category.
7Everything is saved: docs.json, state.json, report.html, report.json.
8The JSON goes back. React shows the issue cards and the URL becomes /a/{id} — reloadable.
Every other button (approve, write, AI, apply) works the same way: React → API route → controller → Analysis::mutate() → save → JSON back → React redraws.

4 · The engine · app/Analyzer

The core objects

Four small classes hold all the data. Learn these first.

Document.php — one file or page

rel (name), kind (html/css/js/json/php/python), text, path or url. tree() gives the parsed HTML.

Issue.php — one problem found

rule, severity, message, file, line, the region (start/end) to change, ruleFix, ai, proposed, status, resolved, written.

Analysis.php — one complete run

Holds documents + issues + scores. create(), load(), save(), saveDocs(), decide() (approve/reject/edit), toArray() (the JSON for React). mutate() = load → change → save, with a file lock so two requests never clash.

LineIndex.php — position ↔ line number

Rules work with byte positions (e.g. 1534). This converts them to line numbers (e.g. line 24) and back, using a fast binary search.

One rule, line by line

From HtmlRules.php (simplified): "every image needs alt text".

foreach ($tree->findAll('img') as $img) {                    // every <img> on the page
    if (! $img->has('alt')) {                                 // no alt attribute?

    }
}

4 · The engine

The life of an issue

Every issue has a status. Your clicks and the Apply step move it along.

pending→ you click ✓ →approved→ Apply →applied→ re-scan →✓ verifiedorstill detected

pending→ Write fix to file →applied + written→ re-scan of that file →✓ written to file

rejected

You clicked ✕. Never applied, but kept in the report.

conflict failed

Two fixes change the same characters, or the file changed after the analysis. Nothing is written — re-run the analysis.

manual

No single place can be edited (e.g. "slow server", "no robots.txt"). Explained only.

no fix yet

Pending, editable, but nothing proposed. The rule can't write one safely (e.g. title too short — it needs real words). Use Explain & fix with AI or ✎ Write fix.

Where the "proposed fix" comes from

rule — written by the rule itself (e.g. add rel="noopener").

ai — written by Ollama, checked by validateFix() first.

user — you typed it with ✎ Edit fix. Always wins.

How "Explain & fix with AI" works

1React sends POST /api/analyses/{id}/ai → AiController@review.
2The issues are marked ai_pending and the server answers immediately (202).
3AiBatch::dispatch() starts a background process: php artisan webqa:ai-batch {id} {issues…}. Local models can take minutes; the browser never waits.
4For each issue, Ollama::review() sends one issue + a few lines of code to /api/chat and asks for JSON: why, fix, corrected, confidence.
5validateFix() checks the answer. storeAi() saves it as a proposal.
6React asks for updates every 1.5 s; the card shows the AI orb while it works, then the result. Stop AI review sets a cancel flag the worker checks.

Safety checks on AI output

  • may change only the flagged region
  • empty / unchanged → ignored
  • much bigger than the original → ignored
  • not the same HTML element → ignored
  • indentation fixed to match your file
  • never applied without your ✓

What the model sees — and what it answers

Never the whole file: one issue plus a few lines around it. Built by Ollama::buildPrompt().

The question — simplified, from the demo site

Detected issue: Image without alt text  [rule a11y-img-alt-missing · Accessibility · high]
Finding: Image "images/acme-logo.png" has no alt attribute.
File: index.html (html), line 9

Context (⟦REGION⟧…⟦/REGION⟧ marks the text you may change)
    <a href="/">⟦REGION⟧<img src="images/acme-logo.png">⟦/REGION⟧</a>

REGION — return the replacement for REGION only, keep indentation.
A rule-based fix was already proposed; improve on it:
    <img src="images/acme-logo.png" alt="Acme logo">

Respond with JSON: why · fix · corrected · confidence

Missing code (e.g. no viewport tag) gets an ⟦INSERT⟧ marker instead. Manual issues must return "corrected": "".

{
  "why": "Screen readers can't describe the logo, so the home link has no name…",
  "fix": "Add alt text naming the business.",
  "corrected": "<img src=\"images/acme-logo.png\" alt=\"Acme Plumbing logo\">",
  "confidence": "high"
}

The request — POST {host}/api/chat, format: json, temperature: 0.15 (steady), num_ctx: 8192, timeout OLLAMA_TIMEOUT. A fixed system prompt: senior web engineer, answer only JSON, never invent facts about the business.

Then validateFix() checks it (slide 16) and storeAi() makes it the proposed fix — unless you already edited or decided the issue.

6 · Fixing

"Write fix to file" — Fixer::writeOne()

One click changes one exact spot in a file on disk. Local folders and files only; you can keep going with the next fix.

1Checks: not a website, not locked, the issue has a fix, the file on disk still matches the analysis, the code at that spot is unchanged. Otherwise it refuses with a clear message.
2Backup once: the original goes to backup/{file} in the analysis folder before the first change to that file.
3Write the new text, then move every other issue in that file to its new byte position and line number. Issues whose code was rewritten become "manual" with a note.
4Keep in sync: docs.json gets the new file text (saveDocs()), so the next write and the bulk Apply see what is really on disk.
5Re-scan that file: the card shows ✓ written to file or a warning if the issue is still detected.

Why the bookkeeping matters

Rules remember issues by byte position. Adding 20 characters at line 9 moves everything after it by 20. Without step 3 the next fix would land in the wrong place.

Safe with bulk Apply

A written issue has written = true. Fixer::apply() skips it in both patch and in-place mode, so a fix is never applied twice.

API: POST /api/analyses/{id}/issues/{issue}/write → AnalysisController@write.

How "Apply" works — Fixer.php + Diff.php

1Collect all approved fixes (not yet written), grouped by file.

4Diff::unified() writes changes.patch (works with git apply).

9 · Extending

How to add your own rule — 3 steps

Example: warn when a page has no <main> element.

1 Catalog.php — describe it

'a11y-main-missing' => [
  'category' => 'Accessibility',
  'severity' => 'low',
  'title' => 'No <main> landmark',
  'why' => 'Screen readers use
    <main> to jump to content.',
  'how' => 'Wrap the main content
    in <main>.',
],

2 HtmlRules.php — detect it

// inside accessibility()
if ($tree->isPage()
    && ! $tree->find('main')) {
  $out[] = Make::issue(
    $doc, 'a11y-main-missing',
    'The page has no <main>.',
    line: $tree->find('body')
          ?->line ?? 1);
}

3 RulesTest.php — prove it

public function test_main_missing()
{
  $this->assertContains(
    'a11y-main-missing',
    $this->rulesFor(
      '<html><body>hi</body></html>'
  ));
}

Run artisan test. Done — UI, scores and report pick it up automatically.

Want an automatic fix too? Pass start:/end: (the region) and fix: (the new text) to Make::issue().

Troubleshooting

Page doesn't open

Is artisan serve still running in a terminal? Port taken → --port=8080 and open that address.

"Ollama is not running"

Start it: ollama serve (or sudo systemctl start ollama), then click ↻ at the top right.

"Model is not pulled"

ollama pull qwen2.5-coder:3b — or pick another installed model in the menu.

AI can't connect though Ollama runs

You started the app with plain php, which is Lerd's container wrapper here. Use /usr/bin/php8.4 artisan serve.

"Not a URL, folder or file"

Check the path for typos; it must exist on this computer.

UI changes don't show

Run npm run build, then hard-reload the browser (Ctrl+Shift+R).

"Your session expired"

Reload the page — Laravel issues a fresh CSRF token.

Something else is broken

Read storage/logs/laravel.log, then run the tests.
