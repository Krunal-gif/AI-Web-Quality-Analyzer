Part 1

The big picture

Before any code: what the tool does and how its pieces fit together.

What the tool does

You give it a target: a website address (https://example.com), a project folder (~/sites/my-theme) or a single file. It reads the HTML, CSS, JavaScript, JSON, PHP and Python, and runs 59 rules over them. Each rule looks for one kind of problem, for example "an image has no alt text" or "a secret API key is written in the code". Every problem it finds becomes an issue.

For each issue the tool shows:

  • Problem: what is wrong, and the exact file and line.
  • Why it matters: a built-in explanation, and optionally a better one from the local AI.
  • Before / After: the original code and a suggested fix. The fix comes from the rule itself or from the AI.

You then approve or reject each fix. Nothing changes until you approve it. Approved fixes are applied, and the tool scans again to prove that each fix really solved its problem. The score shows before → after.

Six categories, 59 rules

CategoryExamples of what it finds
SEOMissing or too-long title, no meta description, no viewport, no canonical, no Open Graph tags, no or several <h1>, noindex, missing robots.txt or sitemap, HTTP errors, slow pages
AccessibilityImages without alt, links and buttons without a name, form fields without a label, no lang, iframe without title, "click here" links, positive tabindex
HTML StructureNo doctype or charset, duplicate ids, old tags like <center> and <font>, unclosed or stray tags, skipped heading levels, inline styles, empty links
ContentLorem ipsum left in the page, repeated words ("the the"), very long sentences, too little text

SecurityHard-coded secrets (AWS, Stripe, Google, GitHub, Slack…), eval, target="_blank" without noopener, http resources on an https page, no HTTPS, incomplete certificate chain, missing security headers (HSTS, CSP, clickjacking…), cookies without Secure / HttpOnly / SameSite

Part 2

Ideas you need first

Short explanations of every idea the project uses. If you already know one, skip it.

2.1 How a web app works

A browser sends a request to a server. A request has a method (GET = read, POST = create or do something, PATCH = change, DELETE = remove) and a URL (/api/analyses). The server sends back a response: a status code (200 OK, 201 Created, 404 Not found, 422 Invalid input, 500 Server error) and a body. The body is HTML for pages, or JSON for data.

POST /api/analyses              ← method + URL
Content-Type: application/json
X-CSRF-TOKEN: 8f3c…               ← proves the request came from our own page

{"target": "samples/demo-site", "pages": 1}     ← request body (JSON)

HTTP/1.1 201 Created              ← status code
{"id": "20261117-094307-demo-site-v7xp", "issues": [ … ], "scores_before": { … }}

This project has two kinds of URLs: pages (/, /a/{id}) that return the HTML that loads React, and an API (/api/…) that returns JSON. React calls the API in the background and redraws the screen.

2.2 PHP in five minutes

PHP code starts with <?php. Variables start with $. This project uses modern PHP 8 features, so it helps to recognise them:

final class Issue                       // final = nobody may extend this class
{
    public const SEVERITY_ORDER = ['critical' => 0, 'high' => 1];   // array with keys (like a JS object)
    public ?array $ai = null;            // ?array = "an array or null"

    public function __construct(
        public string $rule,             // "constructor promotion": declares AND sets $this->rule
        public int $start = -1,          // default value
    ) {}

    public static function make(): self  // static = call it on the class: Issue::make()
    {
        return new self('seo-title-missing', start: 10);   // named argument
    }
}

$issue->ai ??= [];                       // set only if it is null
$names = array_map(fn ($i) => $i->rule, $issues);         // short arrow function
$line = $doc?->lines();                  // ?-> = stop and give null if $doc is null
[$start, $end] = $idx->lineSpan(3);      // unpack an array into two variables

2.3 Composer and autoloading

composer.json lists the PHP packages the project needs. composer install downloads them into vendor/. Composer also creates an autoloader: when the code uses App\Analyzer\Issue, PHP loads app/Analyzer/Issue.php automatically, because of this rule in composer.json:

"autoload": { "psr-4": { "App\\": "app/" } }

So namespace = folder and class name = file name. That is why you never see require in the app code.

2.5 React in five minutes

A React component is a function that returns what to show, written in JSX (HTML-like syntax inside JavaScript). Components receive props (inputs) and can keep state (values that, when changed, redraw the screen).

import { useState, useEffect } from 'react';

function Counter({ label }) {                 // a component; { label } is a prop
    const [count, setCount] = useState(0);    // state: value + function to change it

    useEffect(() => {                         // runs after the component appears
        document.title = `${label}: ${count}`;
    }, [label, count]);                       // ...and again when these change

    return (
        <button className="rounded p-2 text-sm" onClick={() => setCount(count + 1)}>
            {label}: {count}
        </button>
    );
}

// used like an HTML tag:  <Counter label="Issues" />

In this project App.jsx keeps almost all state (the current analysis, filters, AI status). It passes data down to smaller components (Sidebar, IssueCard, CodePane…) as props. When the user clicks something, App.jsx calls the API, gets the new analysis JSON back, and setData(...) redraws everything.

2.6 Vite and Tailwind

Browsers cannot run JSX or Tailwind directly. Vite compiles resources/js/app.jsx and resources/css/app.css into normal files in public/build/.

  • npm run build: compile once (needed before php artisan serve shows the app).
  • npm run dev: keep compiling while you edit; the browser updates by itself.

Tailwind gives you small classes: p-4 = padding, text-sm = small text, dark:bg-ink-900 = background in dark mode. Tailwind finds the classes you use and generates only that CSS.

2.7 Ollama and the AI model

Ollama is a program that runs AI language models on your own computer. It listens on http://127.0.0.1:11434. You send it a prompt (text) and it answers with text. This project asks for the answer in JSON format, with fixed keys (why, fix, corrected, confidence), so PHP can read it.

The model is qwen2.5-coder, a model trained on code. The 3b version (3 billion parameters, ~1.9 GB) is fast enough without a graphics card. 7b is better but slower.

AI can be wrong A model sometimes returns broken code, the same code, or a much bigger change than asked. That is why every AI answer is checked by Ollama::validateFix() before you even see it, and why nothing is written without your approval.

2.8 The key idea of this project: byte offsets

To fix something, the tool must know exactly which characters to replace. It stores every issue's location as two numbers: start and end, counted in bytes from the beginning of the file. Replacing a fix is then simple:

$new = substr($text, 0, $start) . $fix . substr($text, $end);
//      everything before         the fix   everything after
text:    
Hi
↵↵
offset:  0         10               27
                   ^start           ^end       → original =   (17 bytes)
line:    1         2
  • Replace: start < end. The text between them is swapped for the fix.
  • Insert: start == end. Nothing is removed; the fix is added at that point (e.g. a missing meta tag).
  • Advice only: start == -1. The tool can explain the problem but cannot fix it automatically (e.g. "slow server").

Line numbers are only for people. LineIndex converts an offset into a line number when it needs to show one. This is also why the project has its own HTML parser: PHP's built-in DOMDocument forgets offsets.

Check the score yourself

The score formula (from app/Analyzer/Scoring.php) is: each severity has a weight (critical 25, high 10, medium 5, low 2, info 0.5). Add the weights per category to get a penalty. Category score = 100 × e−penalty/60, rounded. Overall = the average of the six category scores.

CategoryIssuesPenalty100 × e−p/60
SEOhigh + medium + medium + low + low10+5+5+2+2 = 24100 × 0.670 = 67
Accessibilityhigh + low10+2 = 12100 × 0.819 = 82
Contentlow2100 × 0.967 = 97
othersnone0100
Overall = (67 + 82 + 100 + 97 + 100 + 100) ÷ 691 ✓
Try it Add <meta name="viewport" content="width=device-width, initial-scale=1"> inside <head> and run the command again. Predict the new SEO score before you look (penalty 14 → 100 × e−14/60 = 79).

5.7 Step 6 · Document and LineIndex

  

  
rel is the name you see (css/style.css). For a website it is made from the URL. kind chooses which rules run.
    The line index and the HTML tree are created only when first needed (??=) and then reused.

  
LineIndex stores the byte offset where each line starts. To find the line of an offset it does a binary search:
    it halves the list each step, so even a 100,000-line file needs only about 17 steps.

  


  
5.8 Step 7 · The HTML parser

  
Why write a parser when PHP has DOMDocument? Because DOMDocument "repairs" the HTML and throws away positions.
    To fix <img src="a.png"> on line 9, the tool must know that tag is bytes 123–156 of the original file.
    HtmlParser walks the text once, finds each <, and records a Node for every start tag:

  

  
<a href="/contact">click here</a>
^start            ^startEnd  ^endTagStart ^end
raw   = '<a href="/contact">'        (exact source of the start tag)
attrs = ['href' => '/contact']        (names lower-cased, values decoded)
children = ['click here']

  
The parser is error-tolerant, like a browser: it closes <p> and <li> automatically, knows
    void tags (<img>, <br>, <meta>…), treats <script> and
    <style> content as raw text, and records stray end tags that close nothing (that becomes an issue). Its regular
    expressions use possessive groups, so a malformed tag cannot make it run forever (there is a test for that).


  
5.9 Step 8 · The rule engine

  

  
    
    
  • HTML files get HtmlRules; every file gets CodeRules (secret detection runs everywhere).
    • 
    
  • try / catch: if one file crashes a rule, it is logged and the other files are still analysed.
    • 
    
  • Site rules run once for websites (HTTP errors, speed, HTTPS, robots, sitemap).
    • 
    
  • Cap: at most 25 issues per rule per file, so 300 "inline style" warnings cannot bury one critical problem.
    • 
    
  • Sort by file order, then line. Then number them I001, I002… and copy the rule's fix into proposed.
    •

5.10 Step 9 · One rule, line by line

  
This is the "image without alt text" rule, inside HtmlRules::accessibility():

    2. 
    
  2. Test: no alt attribute, and the image is not marked decorative (role="presentation" or aria-hidden="true").

    4.

    5. 
    
  5. Fix: HtmlEdit::setAttr($img->raw, 'alt', $alt) returns the same tag with alt="Team" added, keeping everything else as it was.
    6.

    7.

5.11 Code rules: syntax, smells and secrets

  

  
    
    
  • Syntax: JavaScript is checked with node --check, PHP with php -l, Python with ast.parse. The engine
      runs the real tool and reads the line number from its error. JSON uses JsonValidator, which finds the exact line and column,
      because json_decode() only says "invalid".
    • 
    
  • Masking: before looking for ==, eval( or console.log, strings and comments are blanked out
      (maskedLines), so "use == here" in a string or a comment is not reported.
    • 
    
  • Secrets: patterns for AWS, Stripe, Google, GitHub and Slack keys, plus generic password = "…". Obvious placeholders
      such as your-key-here are ignored. The message shows only the first and last characters of a secret.
    • 
  


  
5.12 Step 10 · Scoring

  

  
Why exp() and not "100 minus penalty"? With subtraction, 11 high issues would give a negative score, and 50 issues would score
    the same as 500. The exponential curve makes the first issues cost the most and never goes below 0. Each category counts the same
    in the overall score, so one bad category cannot hide behind five good ones.

  

    
Issues in one categoryPenaltyScore

    
none0100

    
1 low297

    
1 high1085

    
1 critical2566

    
2 critical + 3 high8026

  


  
5.13 Step 11 · Saving safely

  
Two things could change one analysis at the same moment: you clicking Approve, and the background AI saving an answer.
    Without care, one would overwrite the other. Every change therefore goes through mutate():

  

  
    
    
  1. flock(LOCK_EX): wait until no one else holds the lock on this analysis.
    2. 
    
  2. Load the latest state from disk, apply the change, save.
    3. 
    
  3. finally: always release the lock, even if the change threw an error.
    4. 
  

  
save() writes to state.json.tmp and then renames it to state.json. A rename is atomic, so a reader
    never sees a half-written file.

Part 6

  
How the AI and the fixes work

  
From "Explain & fix with AI" to a verified change in your file.


  
6.1 The life of an issue

  

    pending→
    approved or rejected→ Apply →
    applied / conflict / failed→ re-scan →
    resolved ✓ or still detected
  

  

    
FieldMeaning

    
ruleFixThe fix the rule produced (or null). Never changes.

    
aiThe AI's answer: why, fix, corrected, confidence, model, seconds, warning or error.

    
proposed + proposedSourceThe fix that will be applied, and where it came from: rule, ai or user (you edited it).

    
statuspending, approved, rejected, applied, conflict, failed.

    
writtenThe fix was written into the file with "Write fix to file".

    
resolvedAfter the re-scan: true = the problem is gone, false = still detected.

  

  
An AI answer replaces proposed only if you have not edited the fix yourself and the issue is still pending
    (Analysis::storeAi). Your own edit always wins.


  
6.2 Starting an AI review without blocking the browser

  
A local model can take minutes. A web request cannot wait that long. So the controller marks the issues as pending, answers
    at once with 202 Accepted, and starts the work in the background:

  

  

  
With php artisan serve, dispatch starts a separate process: php artisan webqa:ai-batch <id> I001 I002 …
    (the & at the end makes it run in the background). Under PHP-FPM, or in tests, the work runs right after the response
    has been sent. AiBatch::run then takes the issues one by one, most severe first:

  
    
    
  1. Load the analysis without the lock (the model call is slow; the UI must stay usable). Stop if you pressed Stop.
    2. 
    
  2. Save "now working on I003" so the UI can show progress.
    3. 
    
  3. Ask the model (Ollama::review).
    4. 
    
  4. Save the answer under the lock (storeAi). If Ollama cannot be reached, stop early instead of failing each issue.
    5. 
  

  
Meanwhile App.jsx polls: while batch.running is true, it fetches /api/analyses/<id> every
    few seconds and redraws. A worker that crashed counts as finished after 5 minutes (batchRunning()), so AI is never blocked forever.


  
6.3 What the model sees

  
The model gets one issue and only a few lines of context. The region it may change is marked with
    ⟦REGION⟧…⟦/REGION⟧, or the insertion point with ⟦INSERT⟧. This is the end of the prompt built by
    Ollama::buildPrompt:

  

  
Before that comes a system prompt ("You are a senior web engineer… answer ONLY with a JSON object… never invent facts")
    and the task text. If the rule already has a fix, the prompt includes it and asks the model to improve on it.

  

  
    
    
  • 'format' => 'json': Ollama forces the output to be valid JSON.
    • 
    
  • temperature 0.15: low randomness. Code fixes should be predictable, not creative.
    • 
    
  • num_ctx 8192: the model can read up to about 8,000 tokens (the prompt is cut to fit).
    • 
    
  • If the answer is not clean JSON, the first {…} block in it is tried before giving up.
    • 
  


  
6.4 Never trust the model blindly: validateFix

  

  

    
CheckWhy

    
Empty answerNothing to offer

    
Remove ``` fences and the ⟦ ⟧ markersModels like to wrap code in Markdown or copy the markers

    
Same as the originalNot a fix

    
More than 6× the original size (and over 400 bytes)The model rewrote much more than the flagged region

    
Original was an HTML tag but the answer is notThe model returned an explanation or a different thing

A rejected answer keeps the explanation but shows a warning instead of the corrected code.


  
6.5 "Write fix to file" — one fix, right now

  
Fixer::writeOne changes one spot in your file immediately. It refuses unless it is completely safe:

  

  
    
    
  1. Not for websites (the tool cannot edit a server). Not twice. Only issues with a fix.
    2. 
    
  2. The file on disk must be exactly what was analysed. If you edited it in your editor meanwhile, it refuses.
    3. 
    
  3. The text at start…end must still be the original.
    4. 
    
  4. The first time a file is changed, the original is copied to backup/.
    5. 
  

  
After writing, every other issue in that file is moved. If the fix added 12 bytes and 1 line, issues after it get
    start += 12, end += 12, line += 1. An issue whose code overlapped the change can no longer be fixed
    safely: its region is cleared and it asks you to re-run the analysis. Finally the file is re-scanned to set resolved.


  
6.6 "Apply N approved fixes" — all at once

  
Fixer::apply($a, $mode) has two modes:

  

    
ModeYour filesYou get

    
patch (default)untouchedfixed/… copies and changes.patch. Can be run again.

    
inplacechanged (originals in backup/)the analysis is then locked; re-run it to continue. Not allowed for websites.

  

  
The hard part is when two approved fixes touch the same tag, e.g. one adds aria-label and another adds rel to
    the same <a>. Replacing the region twice would lose the first fix. applyToText handles this:

  
    
    
  1. Sort fixes by position; mark a fix failed if its original text is no longer there.
    2. 
    
  2. Group fixes whose regions overlap into clusters.
    3. 
    
  3. Inside a cluster, Diff::mergeEdits compares each version with the original word by word (Myers diff). If their changes
      do not collide, they are merged: <a href="x" aria-label="X" rel="noopener">. If they really collide, the later fix is
      marked conflict and not applied.
    4. 
    
  4. Write the new text and add a unified diff of the file to changes.patch.
    5. 
  


  
6.7 Proving it: the re-scan

  

  
The rules run again on the fixed text. To match "the same problem" before and after, each issue has a fingerprint:
    rule + file + message, with all numbers replaced by # (line numbers change when lines are added).
    If an applied fix's fingerprint is gone → ✓ verified. Still there → still detected. Issues that are new after fixing are
    listed too, so a fix can never quietly create a new problem.


  
6.8 Reports

  
Analysis::writeReports() writes report.json (all data) and report.html, rendered from
    resources/views/report.blade.php. The HTML report has its CSS inside the file and no external files, so you can e-mail it or
    open it offline. Share report in the app sends this file.
